## Key Findings

### 1. Google A2A Protocol Specification (Official, 2026)
- **Three pillars**: Agent Cards (capability advertisement), Tasks (work units), Transport (HTTP/SSE/JSON-RPC 2.0)
- **11 JSON-RPC methods**: SendMessage, SendStreamingMessage, GetTask, SubscribeToTask, CreateTaskPushNotificationConfig, etc.
- **Task object lifecycle**: `submitted` → `working` → `input-required` → `completed` / `failed` / `canceled`
- **Agent Card**: JSON document at `/.well-known/agent.json` declaring capabilities, skills, input/output modes
- **Parts**: A Part MUST contain exactly one of: `text`, `raw`, `url`, `data` (structured JSON)
- **Artifacts**: task output events with unique IDs, revision numbers, and status
- **Implication for UGAFStudio**: Our current `a2a_adapter.py` has a flat dispatch function. It needs a proper Task state machine that mirrors the A2A spec's lifecycle: `submitted → working → completed/failed`.

### 2. Memory & State Persistence for Long-Running Agents (2026)
- **2-tier architecture**: Tier 1 = context window (RAM, recent turns, scratchpad), Tier 2 = persistent store (SQL/vector DB)
- **4-tier model** (most complete):
  1. **Working memory** — current task state (RAM)
  2. **Session memory** — conversation history within a session (Redis/disk)
  3. **Agent memory** — long-term patterns, user preferences, learned behaviors (SQLite/vector DB)
  4. **External memory** — documents, APIs, knowledge bases (RAG)
- **State serialization**: Agent state must survive session boundaries, model swaps, infrastructure restarts
- **State reconstruction**: When loading — agent retrieves relevant memories by recency, importance, relevance score
- **Hermes precedent**: Our current `memory` tool is Tier 3 (agent memory). We have no Tier 1-2 persistence for running tasks.
- **Implication**: A dispatched OpenCode task that runs for 30 minutes — if interrupted, all state is lost. Need a `TaskSession` dataclass that serializes state to disk every N seconds, with auto-recovery on restart.

### 3. Multi-Agent Orchestration Patterns (Production 2026)
- **Fan-out / Fan-in**: One dispatcher fans work to N workers, collects results, synthesizes. Best for parallel QA runs.
- **Supervisor**: A lead agent delegates to specialists and synthesizes. Our Hermes role.
- **Swarm**: Peer-to-peer coordination, emergent behavior. Risky for production.
- **Pipeline**: Sequential stages, each agent does one thing. Our current mode.
- **Debate**: Multiple agents argue, judge selects best. Used for verification.
- **Recommendation**: Implement a `TaskOrchestrator` that supports BOTH fan-out/fan-in (parallel QA across multiple games) AND pipeline (sequential task stages). This is the natural next step after verification + security.

### 4. Google A2A — Task Object Structure
- **Task** has: `id`, `contextId` (session grouping), `status` (state), `history` (message list), `artifacts` (outputs)
- **State transitions** are explicit events, not implicit
- **Push notifications**: SubscribeToTask allows webhook/SSE for status changes — no polling
- **Cancellation**: First-class `canceled` state with reason
- **Implication**: Our current `ConsensusDispatcher` dispatches and waits. A spec-compliant Task object enables async operation: dispatch → get task ID → poll/webhook → collect when done.

### 5. Agent Capability Registry (Agent Cards)
- **Purpose**: Before dispatching, Hermes queries agent's Agent Card to verify it can handle the task
- **Structure**: `name`, `description`, `capabilities[]`, `skills[]`, `input_modes`, `output_modes`, `version`
- **Discovery**: `/.well-known/agent.json` endpoint or inline JSON
- **Implication**: For UGAFStudio's 55+ OpenCode specialists, an Agent Card registry prevents dispatching QA tasks to code-only agents. Each `.opencode/agent/*.md` can embed an Agent Card header.

## Synthesis: A2A-Native Task Lifecycle Architecture

Current state: `a2a_adapter.py` has ~400 lines covering verification + security, but:
- No Task state machine (flat dispatch, no lifecycle tracking)
- No session persistence (state lost on interruption)
- No capability registry (blind dispatch, no agent matching)

Proposed additions:
1. **TaskRecord** — dataclass mirroring A2A Task: id, contextId, status, history, artifacts
2. **TaskStateMachine** — explicit state transitions with validation (submitted→working→completed/failed/canceled)
3. **TaskSession** — serializes running task state to disk (JSON), auto-checkpoint every N seconds, auto-recovery
4. **AgentRegistry** — Agent Card parser and capability matcher (can_handle(task) → bool)
5. **TaskOrchestrator** — fan-out/fan-in + pipeline execution over multiple agents

This brings UGAFStudio's A2A adapter into alignment with Google's A2A specification while adding the state persistence needed for long-running QA tasks (game sessions routinely run 30-90 minutes).
